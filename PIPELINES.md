# F3CF pipelines

This document separates the pipelines that are implemented in the current proof of concept from those that are experimental or expected extensions of F3CF.

Current implemented pipelines:

* [Synthetic data generation using UKB and PGS catalog](#synthetic-data-generation)
* [Site-formatted conversion](#site-formatted-conversion)
* [Federated collaborative factorization](#federated-collaborative-factorization)
* [Embedding exploration](#embedding-exploration)

## Overview

The intended data flow is:

```text
Raw local data
    ↓
Source-specific preprocessing
    ↓
Standardized relation matrices
    ↓
Local multi-relational factorization
    ↓
[Federated aggregation of selected shared entities](#Federated collaborative factorization)
    ↓
Shared latent structure
    ↓
Local or cross-source exploration and analyses
```

Patient-level observations and patient embeddings remain local to the originating institution.

## Implemented pipelines

### Synthetic data generation

The current federated demo generates synthetic multi-site data with `scripts/generate_federated_sites.py`. Phenotype identifiers are taken from the PGS trait catalogue in `data/pgs/pgs_phenotype_effects.csv`, with phenotype labels used to construct structured clinical and genetic reference embeddings.

Three sites are generated by default:

```text
site-1: 120 patients, genetic data available
site-2:  90 patients, genetic data available
site-3: 110 patients, no genetic data
```

Each site observes a slightly different subset of phenotypes. Patient–phenotype observations are generated from latent patient factors and converted to binary outcomes using a logistic model. For sites with genetic information, a second set of latent factors generates standardized continuous PGS values for the same phenotype catalogue. This provides controlled heterogeneity in cohort size, feature availability, and genomic-data availability.

The repository also contains PGS Catalog utilities. `build_pgs_effect_matrix.py` aggregates variant `effect_weight` values from downloaded scoring files to construct a PGS × phenotype reference matrix and associated phenotype/PGS identifiers.

The two data sources play different roles in the pipeline.

#### EHR / clinical side

The intended clinical input is a synthetic UK Biobank-style dataset, used as a stand-in for the local EHR available at a clinic. A site-specific preprocessing pipeline would convert diagnoses, measurements, medications, and other clinical observations into a standardized:

```text
Patient × Phenotype
```

matrix. Phenotypes must then be mapped to the shared identifiers used by F3CF so that equivalent phenotypes can be aligned across institutions.

One important implementation detail: in the current `main` branch, `generate_federated_sites.py` does **not yet read the UKB synthetic dataset directly**. For the runnable demo it generates the patient–phenotype matrices synthetically from latent factors. Connecting the UKB synthetic EHR pipeline to this site format is therefore an upstream preprocessing step rather than part of the current F3CF runner.

#### PGS Catalog / genetic side

The genetic feature catalogue is derived from the **PGS Catalog**. `fetch_pgs_catalog.py` downloads Catalog metadata and scoring files and maps each selected PGS to its ontology-mapped trait. By default, the pipeline selects compact scores, preferring the score with the fewest variants for each trait subject to a maximum variant count.

The downloaded scoring files are then processed by `build_pgs_effect_matrix.py`, which aggregates variant effect weights and produces a PGS × phenotype reference matrix together with shared phenotype and PGS identifiers.

These PGS Catalog phenotype identifiers are also used by `generate_federated_sites.py` as the shared phenotype catalogue. For sites with genetic data, the demo generates continuous patient-level PGS values over the same phenotype columns:

```text
Patient × Phenotype    ← clinical/EHR information
Patient × PGS          ← genetic-risk information
         │
         └── aligned through shared phenotype/trait identifiers
```

In the current demo, sites 1 and 2 contain both clinical and genetic matrices, while site 3 contains only the clinical relation. This deliberately tests whether sites with different data modalities can participate in the same federated analysis.

### Site-formatted conversion

The data interface is implemented in `scripts/federated_cf_data.py`. A federated dataset contains a global:

```text
phenotype_ids.txt
```

and one directory per site containing at least:

```text
site-1/
    patient_phenotypes.csv
```

Sites with genetic information additionally contain:

```text
site-1/
    genome_phenotypes.csv
```

In the current generated demo, `patient_phenotypes.csv` is a binary patient × phenotype matrix, whereas `genome_phenotypes.csv` contains continuous patient-level PGS values for the corresponding phenotypes. The loader also supports a sparse `.npz` representation for genomic relations.

Sites do not need to contain identical phenotype columns. Local column names are mapped to the global phenotype catalogue at load time, allowing each site to contribute only the features it observes while retaining a common indexing of shared phenotypes.

### Federated collaborative factorization

Federated training is launched through `scripts/run_federated_cf_job.py` and coordinated using NVIDIA FLARE. Each site runs `federated_cf_client.py`, which receives the current global phenotype embeddings and fits local row embeddings together with the phenotype vectors needed to reconstruct its local matrices.

For the patient–phenotype relation, binary cross-entropy is used. For the continuous genetic relation, mean-squared reconstruction error is used. Local patient/genetic row embeddings remain at the site; only phenotype embeddings, phenotype masks, and aggregation weights are returned to the server.

The default configuration uses:

```text
32 latent factors
5 federated rounds
20 local epochs per round
learning rate = 0.05
```

The server uses `federated_cf_aggregator.py` to perform size-weighted FedAvg separately for the clinical and genetic phenotype embedding tables. Updates are masked so that a site only contributes to phenotypes it actually observes, and sites without genetic data do not contribute to the genetic table. Embedding vectors are L2-normalized after local optimization and aggregation.

The current main implementation therefore learns separate clinical and genetic phenotype representations; coupling these relations into a single shared phenotype space is an experimental extension rather than part of the default federated runner.

### Embedding exploration

The learned phenotype embeddings can be explored using `scripts/explore_embeddings.py`, which provides a Streamlit-based visualization of the clinical and genetic latent spaces.

The pipeline loads `data/federated/global_phenotype_embeddings.npz`, computes pairwise cosine similarities between phenotype embeddings, and retains phenotype pairs above a user-defined similarity threshold (default `0.65`). The resulting similarity network is constructed with NetworkX and positioned using a weighted spring layout, where stronger cosine similarities exert greater influence on node placement.

Phenotypes are grouped and coloured using the category definitions in `scripts/phenotype_groups.py`, and the network is rendered interactively with Plotly.

For comparison of clinical and genetic structure, the same pipeline constructs a difference network using the genetic layout and classifies edges as:

```text
shared
clinical-only
genetic-only
```

This produces the latent-space network figures used to compare uncoupled and coupled representations.

### Gene–phenotype collaborative filtering analysis

Gene–phenotype associations were obtained from the GWAS Catalog using its ontology-annotated association release (Henrik/Snakefile). Associations lacking mapped genes, mapped traits, or p-values were removed, and records mapping to multiple genes or phenotypes were expanded into individual gene–phenotype pairs. When the same pair occurred in multiple studies, the association with the largest \(-\log_{10}(p)\) value was retained (Henrik/scripts/parse_gwas.py).

The resulting edge list was converted to a binary gene × phenotype matrix and evaluated using collaborative filtering (Henrik/scripts/collab_filter.py). Ten percent of observed associations were randomly masked and excluded from training. The remaining matrix was factorized using truncated singular-value decomposition with 64 latent components. Candidate phenotype associations were reconstructed from the learned gene and phenotype factors, excluding associations already observed during training, and the 50 highest-scoring phenotypes were retained for each gene.

Performance was measured as Recall@50 on the masked associations and compared with a phenotype-popularity baseline, in which candidate phenotypes were ranked by their number of observed gene associations. The complete workflow was implemented as a reproducible Snakemake pipeline with a fixed random seed of 42.
